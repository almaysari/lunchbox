# دراسة معمارية: منصة موحدة لصناديق بريد الشركة على Zoho Mail

> الحالة: معتمدة على توثيق Zoho الرسمي (يوليو 2026) **+ تصحيح جوهري من
> واقع لوحة إدارة Zoho للشركة** — انظر `docs/COMPANY-ENVIRONMENT.md`.
> كل بند معلّم بـ **[موثّق]** له مصدر رسمي مذكور في آخر الملف،
> وكل بند معلّم بـ **[يتطلب تحقق فعلي]** يُحسم بالكشف المدمج في لوحة الإدارة
> (أو `scripts/diagnose.js` المستقلة) على حساب الشركة الحقيقي.

## تصحيح جوهري (2026-07-16): الصندوق المشترك هو الحالة الأساسية

الافتراض الأول («المرحلة 1 تبدأ بصناديق User العادية») **سقط بالدليل**:
لوحة Zoho Admin Console للشركة تُظهر أن جميع العناوين المطلوب ربطها — 20
عنوانًا عبر `exoticcolors.org` و`thetaurus.world` — مصنفة رسميًا تحت
**Groups → Shared Mailbox**، ولا توجد مجموعة User Mailboxes للربط المباشر.

الأثر على المعمارية (مطبَّق في الكود):

1. **الاكتشاف مؤسسي لا فردي:** بعد OAuth بحساب أدمن، تكتشف المنصة كل
   الصناديق تلقائيًا من `GET /api/organization/{zoid}/groups` (لا إدخال يدوي
   لكل عنوان)، وتقارن الناتج بقائمة مرجعية للتحقق فقط.
2. **الفحص الفعلي لكل صندوق:** محرك الكشف يجمع zoid وgroupId وأي accountId
   متاح وAliases والأعضاء والمشرفين وAccess Level وModeration، ثم يجرّب
   قراءة Folders/Messages/Attachments/Sent فعليًا ويخزن الردود الحرفية
   (بعد التعقيم) كدليل.
3. **لا خلط بين المسارات:** Moderation API يُعرض كطابور مراجعة فقط؛
   eDiscovery يُعرض كاستيراد أرشيف؛ ولا يوصف أي منهما بأنه Live Sync.
4. **الاستراتيجية قابلة للتغيير دون فقدان بيانات:** الرسائل مفتاحها هوية
   الصندوق + بصمة التكرار، لا طريقة الاستيراد.

## 1. الهدف

منصة داخلية واحدة تُسجَّل فيها جميع صناديق بريد الشركة الحالية والمستقبلية
(hr@، finance@، marketing@، sales@، support@، procurement@ …) وتوفر:

- مزامنة الأرشيف الكامل: الرسائل القديمة + الجديدة.
- ربط عدد غير محدود من الصناديق أيًّا كان نوعها.
- OAuth رسمي فقط — لا كلمات مرور مخزنة.
- كشف تلقائي لنوع كل صندوق واختيار أفضل مسار وصول رسمي له.
- منع تكرار الرسائل، دعم المرفقات، البحث، والتصنيفات.
- قابلية توسّع (صناديق أكثر، مزوّدون آخرون مستقبلًا).

## 2. أنواع كيانات البريد في Zoho Mail — كما يعرّفها Zoho نفسه

| النوع | تعريفه في Zoho | أين تُخزَّن رسائله؟ |
|---|---|---|
| **User Mailbox** | حساب مستخدم مرخّص له تسجيل دخول | في صندوق المستخدم نفسه |
| **Shared Mailbox** | مجموعة ينشئها الأدمن فقط؛ بلا أعضاء خارجيين؛ بلا Streams؛ **الرسائل لا تُنسخ لصناديق الأعضاء** — تبقى في مخزن مشترك مستقل | مخزن مشترك مستقل (بلا تسجيل دخول خاص) |
| **Distribution List / Email Group** | عنوان واحد يوزّع كل رسالة نسخًا إلى صناديق الأعضاء (يدعم أعضاء خارجيين في الخطط المدفوعة) | نسخة كاملة داخل صندوق **كل عضو** |
| **Streams Group** | مجموعة تفاعلية (منشورات/مهام/مشاركة رسائل) | مساحة Streams + صناديق الأعضاء |
| **Mailbox Delegation** | تفويض مستخدمين للوصول لصندوق مستخدم آخر | صندوق المالك |

**[موثّق]** — صفحات إنشاء المجموعات وإعدادات الـShared Mailbox في Admin Console.

### قيود عامة موثّقة تحكم التصميم

- **حد المعدل:** ~30 طلب API في الدقيقة لكل حساب، وتجاوزه يسبب حظرًا مؤقتًا. **[موثّق]**
- **التصدير الإداري:** الملفات تُحذف بعد 90 يومًا؛ PST للخطط المدفوعة فقط. **[موثّق]**
- **مراكز البيانات:** نطاقات API تختلف (com/eu/in/sa…) — كل اتصال يحمل نطاقه. **[موثّق]**
- **Zoho Mail360:** منصة Zoho الرسمية لتطبيقات البريد (sync + webhooks + APIs موحدة)، لكنها تربط الصناديق عبر **IMAP** — وبالتالي لا تحل مشكلة الـShared Mailbox، ومجانية حتى 10 صناديق ثم مدفوعة لكل صندوق. تصلح كمسار توسّع متعدد المزوّدين، ليست ضرورة اليوم. **[موثّق]**

## 4. المعمارية المقترحة

المبدأ الحاكم: **المنصة لا تفترض نوع الصندوق — تكتشفه، ثم تُسند له استراتيجية وصول رسمية معلنة السبب.**

```
┌─────────────────────────────────────────────────────────────┐
│                        Admin UI / API                        │
│      إضافة صندوق → OAuth → كشف تلقائي → تقرير طريقة الربط     │
└──────────────────────────────┬──────────────────────────────┘
┌──────────────────────────────▼──────────────────────────────┐
│ 1) Mailbox Registry سجل الصناديق                             │
│    (العنوان، النوع المكتشَف، الاستراتيجية، الاتصال، الحالة)      │
├─────────────────────────────────────────────────────────────┤
│ 2) Detection Engine محرك الكشف (منطق diagnose.js نفسه)       │
│    /api/accounts → /api/organization/{zoid}/accounts         │
│    → /groups → تصنيف: user | shared | dl | stream | unknown  │
├─────────────────────────────────────────────────────────────┤
│ 3) Connector Strategies استراتيجيات الوصول (قابلة للإضافة)     │
│    • MailApiConnector      ← User Mailbox (وأي صندوق له       │
│      accountId ظاهر)                                         │
│    • SourceMemberConnector ← DL: قراءة من "صندوق مصدر" معتمد   │
│    • EdiscoveryImportConnector ← Shared Mailbox (أرشيف):      │
│      استيراد ملفات تصدير eDiscovery الرسمية (EML/ZIP)          │
│    • ModerationConnector   ← رسائل المراجعة المعلقة للمجموعات   │
│    • SharedMailboxApiConnector ← فارغة اليوم؛ تُفعَّل يوم يصدر    │
│      Zoho الدعم الموجود على خارطة طريقه                        │
├─────────────────────────────────────────────────────────────┤
│ 4) Ingestion Pipeline خط الاستيعاب                            │
│    Backfill (ترقيم صفحات كامل للأرشيف) + Incremental          │
│    (Webhook أولًا حيث يتوفر EMAIL_RECEIVED، وPolling احتياطًا)  │
│    + Rate Budget: ≤30 طلب/دقيقة لكل حساب + Backoff            │
├─────────────────────────────────────────────────────────────┤
│ 5) Storage التخزين                                           │
│    DB للرسائل والبيانات الوصفية + مخزن ملفات للمرفقات          │
│    Dedup بمفتاحين: (Zoho messageId) و hash(RFC Message-ID +   │
│    التاريخ + المرسل) — الثاني يمنع التكرار بين مصادر مختلفة      │
│    (مثلاً رسالة DL القادمة من صندوقي عضوين)                    │
├─────────────────────────────────────────────────────────────┤
│ 6) Index & Labels الفهرسة والتصنيف                            │
│    بحث نصي كامل + تصنيفات يدوية/آلية (CV، فاتورة، شكوى…)       │
└─────────────────────────────────────────────────────────────┘
```

### لماذا هذا التصميم يلبّي شروطك السبعة

1. **عدد غير محدود من الصناديق:** السجل + عامل مزامنة مستقل لكل صندوق (طابور مهام)؛ إضافة صندوق = صف جديد واتصال OAuth جديد، صفر كود.
2. **الأرشيف الكامل:** Backfill بترقيم الصفحات للصناديق ذات API، واستيراد تصدير eDiscovery الرسمي للـShared — وهذا **ليس حلًا التفافيًا** بل الوظيفة الرسمية المعلنة للأرشفة في Zoho.
3. **OAuth رسمي:** اتصال لكل نطاق صلاحية، refresh tokens مشفرة، صلاحيات قراءة فقط افتراضيًا.
4. **الكشف التلقائي:** محرك الكشف يصنّف العنوان ويطبع للأدمن "هذا النوع، هذه طريقة الربط، وهذا السبب" — نفس منطق `diagnose.js` مدمجًا في المنتج.
5. **منع التكرار:** فهرس فريد مزدوج (messageId + بصمة Message-ID) على مستوى المنصة كلها، لا على مستوى الصندوق فقط.
6. **مرفقات وبحث وتصنيفات:** طبقتا Storage وIndex منفصلتان عن الاستيعاب، فلا تتأثران بنوع المصدر.
7. **التوسّع:** إضافة استراتيجية جديدة (شامل دعم Shared Mailbox القادم من Zoho، أو Gmail/Outlook عبر Mail360 أو APIs مباشرة) لا تمسّ بقية الطبقات.

### قرارات معمارية (ولماذا)

- **ADR-1: Webhook أولًا، Polling احتياطًا.** حد الـ30 طلب/دقيقة يجعل الاعتماد الكلي على Polling غير قابل للتوسع مع عشرات الصناديق؛ `EMAIL_RECEIVED` الرسمي يوصل الجديد فورًا وبتكلفة صفر من حصة الطلبات، ويبقى Polling دوري خفيف لالتقاط ما يفوت الـwebhook.
- **ADR-2: لا `*.integration@` ولا Forward في التصميم.** القراءة الحية للـShared Mailbox غير متاحة رسميًا اليوم (لا IMAP — تصريح Zoho، ولا endpoint رسائل موثّق)؛ بدل الالتفاف، المنصة تغطي أرشيفها بالمسار الرسمي (eDiscovery) وتُبقي فتحة `SharedMailboxApiConnector` جاهزة ليوم صدور الدعم. القرار النهائي لكل صندوق يُتخذ بعد تقرير `diagnose.js` الفعلي.
- **ADR-3: لكل DL "صندوق مصدر" واحد معتمد.** رسائل الـDL تُنسخ لكل الأعضاء؛ القراءة من أكثر من عضو تكرار بلا فائدة، ومن عضو واحد معرَّف بوضوح في السجل تعطي التغطية الكاملة مع مسؤولية واضحة.
- **ADR-4: التخزين محايد للمزوّد.** نموذج الرسالة الداخلي (المعرّفات، الترويسات، الأطراف، المرفقات، التصنيفات) لا يحمل أي حقل خاص بـZoho إلا في جدول ربط، تمهيدًا لأي مزوّد آخر.
- **ADR-5: بيانات كل مركز بيانات تُحترم.** كل اتصال يخزن نطاقي accounts/mail الخاصين به.

## 5. خطة التنفيذ المرحلية

1. **المرحلة 0 — تحقق (قبل أي كود):** تشغيل `scripts/diagnose.js` بحساب أدمن، لحسم البنود المعلّمة [يتطلب تحقق فعلي]: ظهور الـShared في `/api/organization/{zoid}/accounts`، سلوك التفويض، وإمكانية webhook على الصناديق المشتركة.
2. **المرحلة 1 — النواة:** Registry + MailApiConnector + Pipeline + Dedup + تخزين (الكود الحالي في `people-desk/` يُعاد هيكلته ليكون هذه النواة — الواجهة والـOAuth والمزامنة موجودة فعلًا).
3. **المرحلة 2 — الأنواع:** محرك الكشف + SourceMemberConnector + EdiscoveryImportConnector (استيراد EML/ZIP).
4. **المرحلة 3 — الفورية والبحث:** Outgoing Webhooks + فهرسة بحث + تصنيفات.
5. **المرحلة 4 — التوسّع:** صناديق إضافية، تقارير، وتقييم Mail360 إن أُضيف مزوّد ثانٍ.
