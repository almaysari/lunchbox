# قرارات تقنية

## قاعدة التشغيل: PostgreSQL (المتطلب المعتمد) — وسجل مرحلة SQLite المؤقتة

**PostgreSQL هو المتطلب المعتمد** لقاعدة تشغيل منصة مدار في جميع الأوضاع
(development / demo / live / production / integration tests).

استخدام SQLite في النسخ الأولى كان **مرحلة نموذج أولي مؤقتة** اختارها المنفّذ
لتسريع البناء بصفر تبعيات، ولم تكن متوافقة مع متطلب الإنتاج المعتمد، وقد
**استُبدلت بالكامل** في 2026-07-16: لا يوجد اليوم أي `node:sqlite` ولا ملفات
قواعد بيانات محلية في أي مسار تشغيل، والاختبارات التكاملية نفسها تعمل على
PostgreSQL حقيقي (انظر `docs/POSTGRES-SCHEMA-VERIFIED.md`).

## Migrations: استراتيجية Forward-only

لا Rollback تلقائي. كل migration يعمل داخل Transaction واحدة مع تسجيل في
`schema_migrations` (اسم + checksum). تعديل migration مطبّق يفشل بفحص الـchecksum؛
أي إصلاح يُشحن كـmigration جديد. سبب القرار: rollback scripts نادرًا ما تُختبر
بواقعية وتخلق مخاطر فقدان بيانات أكبر من المشكلة التي تحلها؛ استعادة الكوارث
تكون من نسخ PostgreSQL الاحتياطية.

## سرّان منفصلان

`MADAR_ENCRYPTION_KEY` (تشفير التوكنات والأسرار at-rest بـAES-256-GCM) منفصل عن
`MADAR_SESSION_SECRET` (توقيع كوكيز الجلسات HMAC-SHA256) — تسرّب أحدهما لا
يكسر الآخر، وكلاهما ≥ 32 بايت hex بتحقق صارم عند الإقلاع ويرفض تساويهما.

## كلمات المرور

scrypt بمعاملات صريحة (N=2^15, r=8, p=1) بصيغة `scrypt$N$salt$hash`.
لا يوجد أي admin افتراضي: `npm run create-admin` هو المسار الوحيد، لا يطبع
كلمة المرور ولا يقبل أقل من 12 حرفًا.

## تخزين المرفقات

طبقة تجريد (`core/storage.js`): مفاتيح عشوائية 24 بايت (غير قابلة للتخمين،
بلا امتداد)، خارج `public/` بأذونات 0600/0700، منع Path Traversal بالتحقق من
صيغة المفتاح، حد حجم، SHA-256 محفوظ، وكل قراءة تمر عبر مسار API مصرّح
ومسجّل في التدقيق. إضافة S3-compatible لاحقًا = تنفيذ نفس الواجهة
(put/getStream/exists) خلف `MADAR_STORAGE`.


## الأسرار الثلاثة وتدوير مفتاح التشفير (2026-07-17)

- `MADAR_ENCRYPTION_KEY` (+ `MADAR_ENCRYPTION_KEY_V2...` للتدوير): تشفير
  at-rest بـAES-256-GCM. كل قيمة مشفرة تحمل رقم نسخة مفتاحها (`k1:`, `k2:`)،
  والكتابات الجديدة تستخدم أحدث نسخة، والقديمة تبقى قابلة للفك ثم يعاد
  تشفيرها (`reencrypt`). جدول `connections` يسجل `encryption_key_version`.
- `MADAR_SESSION_SECRET`: توقيع كوكيز الجلسات HMAC-SHA256.
- `MADAR_CSRF_SECRET`: توكنات CSRF (double-submit مربوطة بجلسة المستخدم).
- تخزين قيم Zoho: `client_id` نص عادي (معرّف عام)؛ `client_secret` و
  `refresh_token` مشفران at-rest؛ `access_token` في الذاكرة فقط ولا يُخزن
  ولا يُسجل أبدًا. تحديث الـrefresh token محمي بقفل PostgreSQL استشاري
  (`pg_advisory_xact_lock`) يمنع سباقات التحديث بين العمليات المتوازية.


## سياسات أمنية معتمدة (2026-07-17)

### صلاحيات platform_admin على البريد
الأدوار الإدارية تدير المنصة ولا تقرأ محتوى البريد تلقائيًا: العناوين والنصوص
والمرفقات تتطلب Mailbox Grant صريحًا لكل مستخدم بمن فيهم platform_admin.
الأدوار تمنح الـMetadata والإدارة فقط (سجل الصناديق، أدلة الكشف، مهام
المزامنة). الأدمن يستطيع منح نفسه Grant لكن كل تعديل صلاحيات يسجل في
التدقيق (`admin.grant.set`). لا Dual control في هذه النسخة (منظمة بأدمن
واحد) — يعاد التقييم عند توسع الفريق. التدقيق لا يسجل محتوى البريد أبدًا.

### سياسة 404 (منع التعداد)
مستخدم بلا صلاحية على معرف مورد محدد (mailbox / canonical / occurrence /
attachment / تقرير كشف) يتلقى 404 مطابقًا تمامًا للمعرف غير الموجود.
الاستثناء الموثق: endpoints الإدارية المحمية بالدور تعيد 403 لأنها لا
تكشف وجود أي مورد محدد.

### Canonicalization v2 (canonical_hash_version)
Message-ID أولًا؛ وعند غيابه بصمة من (from | to | cc | subject | timestamp
| hash(snippet) | has_attachments). BCC مستثنى عمدًا (بيانات envelope خاصة
بالـOccurrence). أي تغيير مستقبلي = نسخة جديدة + migration، والصفوف القديمة
تحتفظ بنسختها ولا يعاد دمجها.

### خصوصية الـEnvelope
To/CC/BCC كما رأتها نسخة صندوق معيّن تُخزن على الـOccurrence وتُعرض فقط
لمستخدمي ذلك الصندوق — لا fallback إلى حقول الـCanonical (كان الـfallback
يسرّب CC وأمسكه الاختبار فأزيل).

### Crash Recovery لمهام المزامنة
عند الإقلاع، أي مهمة بقيت `running` بسبب توقف غير نظيف تتحول إلى `paused`
(المؤشر محفوظ → استئناف آمن). اخترنا paused لا queued/failed حتى لا يستأنف
شيء دون قرار مشغّل صريح.

### Migrations في Docker
الـEntrypoint يشغّل الـMigrations قبل التطبيق، والمشغّل يحمل قفل PostgreSQL
استشاري (session-level) — عدة نسخ تبدأ معًا تطبقها مرة واحدة بالضبط
(مُختبر بتشغيلين متزامنين في CI).

### حالة S3
Local Storage: منفذ ومختبر. S3-compatible: **غير منفذ** — العقد مصمم فقط
(`core/storage-s3.js`)، واختيار `MADAR_STORAGE=s3` يوقف الإقلاع برسالة
واضحة ولا يعود تلقائيًا إلى Local. signedUrl في Local يعيد null (غير مدعوم
عمدًا) — كل قراءة تمر حصريًا عبر مسار API المصرّح.

### اعتماد eDiscovery مسارًا وحيدًا لأرشيف الصناديق المشتركة (2026-07-17)

القرار اتُخذ بعد مراجعة الأدمن لمصفوفة الوصول الحرفية (زر «مصفوفة الوصول
لكل Endpoint» — مبنية من `detection_reports` بلا أي نداء جديد): على حساب
الشركة الحقيقي، 34 صندوقًا مغطى و169 صف دليل:

- **صفر** قراءة حية لأي صندوق مشترك (`liveSharedMailboxReadProven: false`).
- 66 محاولة `folders` بمعرفَي mailboxId وzgid لكل الصناديق الـ33 رُفضت
  حرفيًا: `404 "Invalid Input" / "Account id N is invalid"`.
- 33 صندوقًا بلا accountId في `organization/{zoid}/accounts` أصلًا —
  وعائلة رسائل Zoho Mail كلها accounts-scoped، فلا معرف صالح للمحاولة.
- 33 نقطة `groups/{zgid}/messages` أعادت 200 لكنها طابور المراجعة
  الموثّق فقط (المحتوى المعاد = الرسائل المحتجزة حصرًا، يطابق عدادات
  الـModeration) — ليست الأرشيف.
- **الدليل المضاد الحاسم**: النقاط نفسها نجحت كاملة (folders/messages/
  content/attachmentinfo كلها 200 ببيانات) على صندوق المستخدم الأدمن
  الوحيد الذي يملك accountId — أي أن التوكن والنطاقات سليمة، والفشل
  بنيوي في المزوّد لا في التصريح.

النتيجة المعتمدة: القراءة الحية لرسائل الصناديق المشتركة غير ممكنة عبر أي
endpoint رسمي مختبَر؛ مسار الأرشيف الرسمي الوحيد هو تصدير eDiscovery
واستيراده (ZIP/EML) عبر «رفع أرشيف ZIP»، مع طابور المراجعة للمحتجز فقط.
يُعاد النظر تلقائيًا إذا أظهرت مصفوفة لاحقة أي `success` لصندوق مشترك.

### لماذا لا يمكن أتمتة تصدير eDiscovery نفسه (إثبات موثّق، 2026-07-17)

سؤال فُحص بالوثائق الرسمية قبل الإجابة: هل لتصدير eDiscovery أي API أو
واجهة مدعومة قابلة للبرمجة؟ **النتيجة: لا.**

1. **فهرس Zoho Mail API الرسمي** (zoho.com/mail/help/api/) يعدّد فئات
   الـAPI كاملة: Organization, Domain, Users, Mail Policy, Accounts,
   Folders, Labels, Email Messages, Signatures, Threads, Tasks,
   Bookmarks, Notes, Logs — **لا توجد فئة eDiscovery أو Export أو
   Backup** ضمن الواجهات المنشورة.
2. **فضاء نطاقات OAuth الموثّق** (`ZohoMail.*` في using-oauth-2.html
   وscope.html) لا يحتوي أي نطاق `ediscovery` — أي لا يمكن حتى طلب
   تصريح لهذه الوظيفة عبر OAuth.
3. **وثائق eDiscovery نفسها** (email-investigations.html,
   manage-ediscovery.html) تصف التصدير حصريًا كتدفق داخل Admin Console:
   eDiscovery → Investigations/Export → «Export search results» →
   تبويب Exports → تنزيل ZIP/PST — مع **إدخال كلمة مرور الأدمن يدويًا
   عند التصدير** (حاجز بشري مقصود من Zoho)، وخيار كلمة تشفير للملف،
   وتنظيف الملفات المصدَّرة بعد 90 يومًا. لا ذكر لأي endpoint.
4. أتمتة البوابة بجلسة متصفح (تسجيل دخول + MFA + إعادة كلمة المرور)
   ليست «واجهة مدعومة»، وتخالف قيود أمان المشروع (لا كلمات مرور خارج
   OAuth الرسمي) — مرفوضة مبدئيًا.

الحد الأدنى البشري المعتمد: (أ) تشغيل التصدير من بوابة eDiscovery
وتنزيل الـZIP، (ب) اختيار الملف/الملفات في «رفع أرشيف ZIP». كل ما بعد
ذلك آلي بالكامل (فك، تحليل EML، مجلدات، dedup، مرفقات+حجر، فهرسة، تقرير
sync_jobs). الرفع يقبل أجزاء تصدير متعددة دفعة واحدة، وحد الحجم لكل جزء
`MADAR_MAX_UPLOAD_MB` (افتراضي 1024MB) برسالة 413 واضحة.

### تشخيص المزامنة الحية بالأدلة (2026-07-17)

مشكلة: فشل المزامنة كان يظهر كـ"internal error" بلا سياق. السبب الجذري
ليس عطلًا في الجلب بل **غياب طبقة رصد**: معالج 500 في server.js كان يعيد
'internal error' في وضع live ويسجّل الرسالة فقط دون Stack، والموصل يرمي
أخطاء نصية مسطّحة تفقد سياق HTTP.

الإصلاح:
- `sync_diagnostics` (Migration 007): صف لكل دورة مزامنة لكل صندوق يحمل
  المرحلة (connect/list_folders/fetch_messages/db_tx/routing/body/
  attachments/done)، آخر Endpoint، عدّادات القراءة/الإدراج/التجاهل/
  التوجيه، وعند الفشل: نوع الخطأ، الرسالة، **Stack كامل**، وسياق مُصنّف
  (HTTP status/response-sample من ZohoApiError، أو SQLSTATE/constraint من
  أخطاء pg، أو Message-ID/mailbox/decision من التوجيه).
- كل استثناء يحمل الآن `traceId` يظهر في حالة الوظيفة والصندوق والرد.
- معالج 500 لم يعد يعيد 'internal error': يعيد الرسالة الحقيقية (مع تعقيم
  أي بيانات اعتماد) + errorClass + errorId + traceId ويسجّل Stack كاملًا.
- صفحة Diagnostics في اللوحة: آخر دورة لكل صندوق + آخر الأخطاء + عارض
  Stack كامل لكل trace.
- إثبات حي: خادم فعلي، مزامنة جلبت 250 رسالة/83 مرفقًا من Zoho (المحاكي)،
  حُفظت في القاعدة، وظهرت في واجهة البريد بعد منح صريح (سياسة عدم قراءة
  الأدمن بلا Grant تعمل)؛ وصندوق معطوب أظهر السبب الحقيقي + Stack كامل
  عبر /diagnostics بدل 'internal error'.

ملاحظة صدق مسجّلة: messages/view الحقيقي لا يحمل حقل RFC Message-ID، لذا
المزامنة الحية تعتمد بصمة v2؛ الموصل يقبل عدة أسماء للحقل إن توفّر مستقبلًا.

### تشخيص Live Sync وإصلاح الحالة العالقة "syncing" (2026-07-17)

بلاغ «فشل داخلي في Live Sync». التشخيص المبني على أدلة الأدمن (تفاصيل
صندوق m.almaysari@) أبطل فرضية بناء الموصل: الفحص سليم وworkingId موجود
(accountId=8696684000000008002، مجلدات 11، رسائل/محتوى/مرفقات كلها 200).
العَرَض الحقيقي كان الحالة عالقة على "syncing".

**السبب الجذري (Root Cause)**: `recoverStaleJobs` (في modules/mail/sync.js،
أُضيف بـ Live Sync في Commit cf1b72d) كان يعيد المهام العالقة `running`
إلى `paused` عند الإقلاع، لكنه **لا يصحّح صف الصندوق**؛ فأي صندوق تُرك
status='syncing' بإعادة تشغيل غير نظيفة (أو أثناء مزامنة طويلة قُطعت)
يبقى عالقًا بصريًا على "syncing" إلى الأبد.

**التصحيح**: `recoverStaleJobs` يعيد الآن كل صندوق status='syncing' إلى
'ready' مع ملاحظة استئناف، بجانب إيقاف المهمة مؤقتًا. مثبت باختبار.

**طبقة الرصد (لمنع تكرار الغموض)**: جدول sync_diagnostics (Migration 007)
يسجّل لكل دورة: المرحلة (connect/list_folders/fetch_messages/db_tx/
routing/body/attachments/done)، آخر Endpoint، HTTP status، عيّنة استجابة
معقّمة، عدّادات (مقروء/مُدرج/متجاهل/موجّه)، وعند الفشل: نوع الاستثناء،
الرسالة، الـStack الكامل، SQLSTATE/Constraint، وسياق التوجيه. أخطاء Zoho
تُرفع كـ ZohoApiError تحمل endpoint+status+عيّنة. معالج 500 لم يعد يعيد
"internal error": يُصدر errorId متتبَّعًا + السبب الحقيقي المعقّم +
traceId. صفحة «تشخيص المزامنة» تعرض ذلك مع الـStack الكامل لكل trace.

**إثبات حي** (خادم فعلي، وضع demo): مزامنة نجحت (250 رسالة، traceId)،
والرسالة ظهرت في واجهة البريد بعد منح القراءة (subject/from/body)،
وصف sync_diagnostics سجّل outcome=ok stage=done. ثم أُفسد workingId عمدًا
فظهر الفشل الحقيقي حرفيًا: stage=list_folders، HTTP 404،
endpoint=/api/accounts/9999999999/folders، عيّنة «Account id … is invalid»،
وStack كامل عبر zoho-mail-api.js → sync.js → routes.js — بلا أي
"internal error".

### Canonical Identity v3 — بصمة تعمل على بيانات Zoho الحقيقية (2026-07-17)

**المشكلة (من أدلة حقيقية)**: `messages/view` الحقيقي لا يعيد Message-ID
(RFC) إطلاقًا — حقوله: fromAddress/sender/subject/sentDateInGMT/
receivedTime/toAddress/ccAddress/size/messageId(داخلي)/hasAttachment…
بينما أرشيف eDiscovery (EML) يحمل Message-ID. المفتاح القديم v2 كان
يعتمد Message-ID أولًا، فكانت النسخة الحية (بلا Message-ID، بصمة) والنسخة
الأرشيفية (بـMessage-ID) لنفس الرسالة تنتجان canonical مختلفَين =
تكرار عند دمج Live مع Archive.

**القرار — fp3**: هوية الرسالة تُحسب بنفس الطريقة من كل المصادر، من حقول
message-intrinsic ثابتة عبر النسخ فقط:
`sha256( from-emails | SENT-second | subject | to-emails | cc-emails )`
- **وقت الإرسال** (`sentDateInGMT` حيًّا / ترويسة `Date:` في EML) لا
  وقت الاستلام (الذي يختلف لكل صندوق)، مقرَّبًا للثانية (دقة RFC2822).
- from/to/cc تُختزل إلى عناوين بريد فريدة مرتبة (إزالة الأقواس والأسماء
  والترتيب).
- **مستبعَد عمدًا**: messageId الداخلي وreceivedTime وsize (كلها per-copy)،
  وsnippet/body وعلم المرفقات (قد يختلف تمثيلها بين Live والأرشيف فيكسر
  التقارب). BCC يبقى per-occurrence، ليس هوية. Message-ID يُخزَّن للأدلة
  الجنائية فقط.

**الإثبات (بقيم Zoho حقيقية، لا Mock)** — `scripts/verify-canonical-fingerprint.js`
يستخدم دالة dedupHash المشحونة نفسها على رسائل طابور المراجعة الحقيقية
(all@exoticcolors.org): (1) إعادات الإرسال الحقيقية لنفس العنوان بأوقات
مختلفة تبقى منفصلة؛ (2) رسائل مختلفة → بصمات مختلفة؛ (3) **التقارب**: سجل
Live (بلا Message-ID) وEML أرشيفي (بـMessage-ID) لنفس الرسالة الحقيقية →
بصمة متطابقة؛ (4) مستقلة عن الصندوق؛ (5) إعادة الاستيراد ثابتة. ومُغطّى
في حزمة الاختبارات (32/32) بدمج حقيقي Live↔Archive → 0 مستورد/1 تكرار
مُنع، مع قيد فريد (mailbox_id, canonical_message_id).

**مقايضة مقبولة موثّقة**: رسالتان مختلفتان فعلًا تشتركان في (نفس المرسل،
نفس الثانية بالضبط، نفس العنوان، نفس المستقبلين) ستندمجان — احتمال شبه
معدوم عمليًا (تُعدّ عندها نسخة مكررة). المخاطرة التجريبية الوحيدة: لو
اختلف `sentDateInGMT` الحي عن ترويسة `Date:` الأرشيفية بأكثر من ثانية لن
تتقاربا؛ كلاهما مشتق من وقت الإرسال الأصلي نفسه فيُفترض تطابقهما بدقة
الثانية — يُراقَب على بيانات حقيقية عند أول استيراد أرشيف فعلي.

الإصدار v3 يُطبَّق على الاستيعاب الجديد فقط؛ صفوف v2 القديمة تحتفظ
بإصدارها ولا يُعاد دمجها (لا تغيير مخطط — العمودان موجودان).

### إغلاق Canonical Identity v3 — الآلية والقياس (مفتوح حتى أرشيف حقيقي) (2026-07-17)

الحالة المعتمدة: **Implemented, CI Passed, Test-Proven, Pending Production
Archive Validation**. القرار لا يُغلق قبل نجاح المقارنة على أرشيف eDiscovery
حقيقي. بُنيت الآلية التي ستنفّذ الحكم:

**1) التطبيع الموحّد (`normalizeForFingerprint`، مصدر وحيد للهوية وللمُتحقِّق)**:
subject: lowercase + طيّ المسافات + trim. العناوين: استخراج addr-spec فقط
(إزالة Display Names)، أي فاصل (، ؛ مسافة سطر) يُعالَج بالاستخراج لا التقسيم،
إزالة التكرار، ثم ترتيب. الوقت: انظر (2).

**2) معالجة الوقت بدقة**: رقم/سلسلة أرقام = epoch ms كما هو (GMT أصلًا)؛ خلاف
ذلك `Date.parse` (RFC2822/ISO تحمل offset صريحًا ⇒ UTC مطلق، وDST مضمَّن في
الـoffset)؛ التقريب للثانية (ترويسة Date بلا أجزاء ثانية)؛ missing/invalid ⇒ 0
مع تسجيل الرسالة `time_unlinkable`.

**3) Collision Metrics داخل النظام (Migration 008 `fingerprint_metrics`)**:
تُسجَّل لحظة الاستيعاب باستخدام RFC Message-ID كمرجع جنائي مستقل:
`false_merge_prevented` (نفس fp3 لكن RFC مختلف ⇒ يُمنع الدمج بتمليح المفتاح
بالـRFC، بلا فقدان)، `false_split_detected` (نفس RFC تحت fp3 مختلفين)،
`duplicate_prevented`، `time_unlinkable`. Endpoint
`/api/mail/fingerprint-metrics` يعرض الأرقام الستة + Correlation Confidence،
وصفحة إدارة مخصصة. RFC Message-ID يُخزَّن دائمًا كدليل جنائي وإن لم يكن المفتاح.

**4) تقرير الإثبات الإنتاجي (`scripts/validate-fp3.js <folder>`)**: يقارن Live
(المزامَن في القاعدة) مع أرشيف ZIP الحقيقي على تقاطعهما، ويُخرج: matched_by_fp3،
unmatched، false_merges، false_splits، duplicates_prevented، unlinkable +
Correlation Confidence، ويشترط ≥100 رسالة في المصدرين. يستخدم RFC Message-ID
مرجعًا مستقلًا (fp3 لا يحكم على نفسه). **حُقِن ونجح على 120 حية + أرشيفها +5
جديدة**: matched 120 / unmatched 5 / false 0 / confidence 1 / PASS — إثبات أن
الأداة تعمل؛ الأرقام الحقيقية تأتي من أول تصدير eDiscovery فعلي عندك.

**5) خطة fp2→fp3 (`scripts/reconcile-hash-versions.js`، dry-run/--apply)**: لكل
canonical من v2 يُعاد حساب fp3 من حقوله؛ إن وُجد توأم v3 تُنقل النسخ/المرفقات
إليه (بأمان عبر قيود التفرد) ويُحذف الصف القديم، وإلا يُرقّى في مكانه إلى v3.
النتيجة: canonical واحد لكل رسالة مهما كان الإصدار الذي استوعبها أولًا — لا
ازدواج fp2↔fp3 دائم. **مُختبَر**: توأم v2 اندمج في v3، صفر v2 متبقٍّ، بلا فقدان.

المخاطرة التجريبية الوحيدة الباقية (تطابق `sentDateInGMT` الحي مع ترويسة `Date:`
الأرشيفية بدقة الثانية) ستُقاس مباشرة بتقرير (4) على بياناتكم: أي انزياح سيظهر
كـ unmatched تعود أسبابه إلى فرق الثانية، وحينها نعالجه بنافذة تسامح موثّقة.

## لماذا "بريد جديد لا يظهر" رغم نجاح Discovery ووجود workingId — عطلان حقيقيان في Live Sync

التشخيص لم يكن grant فقط. مراجعة مسار الجلب كشفت عطلين يوقفان ظهور البريد الجديد
حتى مع worker يعمل وDiscovery ناجح:

**العطل (أ) — هشاشة الترتيب في الصفحة الأحدث.** كان مسح "الصفحة الأحدث"
التزايدي يتوقف عند أول رسالة معروفة (`break` على أول مكرّر). لكن نقطة نهاية Zoho
`messages/view` **لا تضمن ترتيبًا** (الافتراضي غير موثّق وقد يتداخل)، فإذا وصلت
رسالة جديدة في موضع **بعد** رسالة مخزّنة سابقًا، يتوقف المسح قبلها ولا تُدرَج أبدًا.
**الإصلاح**: مسح الصفحة الأحدث **كاملة** دائمًا (بلا `break`)؛ إعادة مسح صفحة واحدة
كل دورة رخيصة (dedup هو `ON CONFLICT DO NOTHING` واحد) وتضمن التقاط أي رسالة جديدة
ضمن النافذة الأحدث بصرف النظر عن الترتيب. الصحة لم تعد تعتمد على ترتيب المزوّد.

**العطل (ب) — توقّف دائم بسبب دورة ماتت في منتصفها.** دورة تُقتل في منتصفها تترك
صف `sync_jobs` بحالة `running` والصندوق `syncing`. في الدورة التالية يرمي
`createJob` خطأ "already running"، فيصنّف الـworker الصندوق `skippedBusy` **ولا
يُزامَن أبدًا** حتى إعادة تشغيل كاملة (recoverStaleJobs يعمل عند الإقلاع فقط).
**الإصلاح**: `reconcileStale` يُستدعى في **رأس كل دورة worker** — يوقف مؤقتًا (paused)
أي job عالق `running` بلا تقدّم لأكثر من 15 دقيقة (المؤشر محفوظ فيُستأنف) ويُحرّر
الصندوق من `syncing`، مع **بوابة عمرية** لئلا تُجهَض مزامنة طويلة مشروعة. لم يعد
هناك توقّف دائم صامت.

**الإثبات**: اختبار يفشل مع `break` ويمرّ بدونه — يحقن رسالة جديدة في الموضع 2
(بعد رسالتين مخزّنتين) ويثبت التقاطها؛ ويثبت أن job عالق 20 دقيقة يُستأنف بينما job
عمره دقيقة لا يُمَسّ. 35/35 أخضر.

**أداة التشخيص على التنانت الحي (`scripts/livesync-doctor.js`)**: تُشغَّل داخل حاوية
التطبيق —
`docker compose exec app node scripts/livesync-doctor.js <address> --force --grant`
— تفرض دورة مزامنة حقيقية، تجيب على الأسئلة السبعة من القاعدة الحية (worker،
دورة حديثة، جُلب من Zoho، inserted/cursor/dedup، محفوظ-لكن-محجوب، syncing، أحدث
diagnostics بـtraceId+read/inserted/skipped)، ثم **تُثبت** بلوغ رسالة حقيقية إلى
واجهة القارئ عبر نفس مسار الصلاحيات، وتطبع حُكمًا حاسمًا. بلا محتوى رسائل وبلا توكنات.

## حالة الـworker تُقرأ من نبضة في قاعدة البيانات، وأعطال النقل تُشخَّص كاملة (HTTP 0)

**دليل حقيقي من الخادم**: `MADAR_LIVE_SYNC=true` وسجل التطبيق يؤكد
"live sync worker started"، ومع ذلك قال الـdoctor "worker OFF". السبب: الـworker
يعمل داخل العملية الرئيسية، وحالته كانت في **ذاكرة تلك العملية فقط**؛ الـCLI عملية
منفصلة فيقرأ singleton فارغًا. القرار: **نبضة في القاعدة** (`sync_worker_heartbeat`)
يكتبها الـworker عند البدء وكل دورة؛ `workerStatus()` يقرأ منها — "يعمل" = enabled
**و** النبضة حديثة (خمول > دورتين + مهلة ⇒ العملية الرئيسية ماتت ⇒ ليس يعمل، ويُكتشف
عبر العمليات). كل دورة تُسجَّل في `sync_worker_cycles` مع `source`
(`worker`/`cli`/`manual`)، فيثبت نجاح/فشل الـworker الرئيسي **مستقلًّا** عن أي دورة
CLI مفروضة.

**العطل الحقيقي: `list_folders` فشل بـHTTP 0.** "HTTP 0" يعني أن الطلب **لم يبلغ HTTP**
أصلًا (DNS/TLS/socket/timeout). كان `get()` يبتلع الخطأ في سطر واحد. الآن يستخرج
سلسلة الأسباب كاملة (undici يضع السبب الحقيقي في `err.cause`): `kind` مصنّف
(dns/tls/connection_refused/connection_reset/timeout/unreachable) +
`code/errno/syscall/hostname/address/port` + `causeChain` + `stack`. تنتقل عبر
`ZohoApiError` (رسالة تسمّي السبب: «transport failure (dns ENOTFOUND)» بدل «HTTP 0»)
إلى `sync_diagnostics.response_sample`، فيعرضها الـdoctor في الفحص 3 و7 وفي الحُكم:
«مشكلة شبكة/DNS/TLS في الوصول إلى Zoho، ليست خطأ تطبيق». **مُختبَر**: 36/36 أخضر.

## جذر «HTTP 0» على مستوى التطبيق: فصل المراحل والتصنيف الكامل (بعد براءة الشبكة)

net-diagnose من داخل حاوية الإنتاج برّأ النقل نهائيًا (DNS/TCP/TLS/HTTPS كلها
سليمة، بلا proxy). التحقيق الممنهج في مسار list_folders كشف الجذر في الكود:
`get()` كان يلف مرحلة OAuth (`token()`) ومرحلة الطلب (`fetch`) بقوس catch واحد —
فأي فشل في **الحصول على token** (رفض التجديد invalid_grant، تعذّر فك تشفير
refresh token بعد تغيّر MADAR_ENCRYPTION_KEY، غياب refresh token) كان يُختم
زورًا «HTTP 0 transport» رغم أن **أي طلب لم يغادر العملية أصلًا**.

**الإصلاح (لا سلوك جديد — تشخيص صادق):** فصل المراحل oauth/fetch/read في `get()`؛
أخطاء OAuth الآن `ZohoAuthError` مصنّفة (`oauth_token_missing` /
`oauth_token_decrypt_failed` / `oauth_refresh_failed`)؛ استجابات HTTP تُصنَّف
(`oauth_scope_denied`, `http_401/403/429`, `zoho_account_mismatch`,
`zoho_api_error`, `malformed_response`)؛ فشل الشبكة يبقى مصنّفًا بطبقته؛
المهلة `request_timeout` مع دليل الإجهاض (أُنشئ AbortSignal؟ انطلق؟ لماذا؟
كم مضى مقابل المهلة؟). **الاستثناء الأصلي يُحفَظ كاملًا** (name/code/errno/
syscall/hostname/سلسلة cause/stack — بعد تعقيم أي أسرار) في
`response_sample.originalError`، والتصنيف في عمود `classification`
(migration 012). دورة حياة الـtoken موثّقة بالأدلة: المصدر (memory/postgres_cache/
refresh)، بصمة sha256 مقتطعة (لا القيمة أبدًا)، expiry، قرار التجديد وسببه
وتوقيته ونتيجته.

**أداة الحسم (`scripts/zoho-path-diagnose.js`)**: Test A (مزوّد token الإنتاجي
نفسه + نفس connector مباشرة) وTest B (مسار Live Sync الحقيقي syncMailbox) مع
مقارنة بصمة/مصدر/انتهاء الـtoken وaccountId ومضيف مركز البيانات والتصنيفين،
و`--repeat N` لمطاردة التقطّع، وتفسير آلي بقواعد الحسم. **برهان تشغيلي**: شغّلناها
ضد خادم حقيقي بعملية منفصلة ذات مفتاح تشفير مغاير عمدًا — صنّفت
`oauth_token_decrypt_failed` باتساق 3/3 على المسارين بالتفسير الصحيح؛ الكود
القديم كان سيسمّي هذه الحالة نفسها «HTTP 0». وهي المرشح الأول لجذر الحالة
الحقيقية (حاوية أعيد إنشاؤها بمفتاح جديد على بيانات قديمة).

الاختبارات تثبت كل صنف + التعافي عبر نفس المسار + عدم تسرب أي token إلى أي
دليل (فحص نصي صريح على الرسائل/العينات/الـstack).

## k1 لم يُفقد قط: عيب تهيئة الـkeyring في عمليات CLI + الشفاء الذاتي للـjobs العالقة

**تصنيف التنانت الحقيقي** أظهر A=`oauth_token_decrypt_failed` («No encryption
key for version k1») وB=«job 30 already running». التتبع الرجعي أثبت:

**(1) k1 موجود — الفشل كان في أداة التشخيص نفسها.** بنية التشفير:
`MADAR_ENCRYPTION_KEY` هو الإصدار 1 حُكمًا (`env.js`)، البادئة `k1:` في النص
المشفر، والمفاتيح التاريخية عبر `MADAR_ENCRYPTION_KEY_V2...`. والخطأ «version
k1» لا يصدر إلا عن **keyring فارغة**. المستدعي الوحيد لـ`cryptoCore.init()` كان
`server.js` — كل CLI يفكّ تشفيرًا كان يعمل بلا أي مفتاح محمَّل، فيفشل على كل
تنانت مهما كان المفتاح سليمًا. **العلاج**: `core/bootstrap.js` — نفس مسار تهيئة
الخادم — يُستدعى أول سطر في كل CLI يلمس أسرارًا، واختبار انحدار بعملية طفل
حقيقية يعيد إنتاج الخطأ الحرفي بلا bootstrap ويفكّ التشفير معه، ويتحقق نصيًا أن
السكربتات الثلاثة تستدعيه. لا استرداد توكنات ولا إعادة تفويض مطلوبة من حيث
المبدأ — الحكم النهائي بعد إعادة تشغيل التشخيص المصحح على التنانت.

**(2) جذر «job عالق يحجب المزامنة» ثلاثي:** (أ) الاستئناف كان يُبقي
`started_at` الأصلي القديم فيبدو job المستأنَف الحي «قديمًا» زائفًا أمام
`reconcileStale` — الآن `started_at = now()` عند كل محاولة (البداية الأصلية في
`created_at`)؛ (ب) `createJob` كان يرمي «already running» حتى لمحاولة ميتة —
الآن **شفاء ذاتي عند الدخول** بنفس شرط الـ15 دقيقة: إيقاف مؤقت واستئناف في
المكان، بحراسة حالة + `RETURNING` ضد سباق الاكتمال (لا إحياء job مكتمل
كزومبي)، وإن تغيّرت الحالة أثناء السباق نقرأ الواقع ونتصرف بحسبه؛ (ج) job
عالق بـ`queued` (انهيار بين الإدراج والتشغيل) يُشفى بالطريقة نفسها. الحماية من
التزامن باقية: job حي (عمره < 15د) ما زال يرفض تشغيلًا موازيًا — كلها مثبتة
باختبارات فاشلة-أولًا. أداة `scripts/job-inspect.js` القرائية تشرّح أي job على
التنانت (عمر المحاولة، النبضة، أقفال advisory، idle-in-transaction، وحكم
liveness) بلا أسرار.

## lease على الـjob: القِدم يقيس الموت لا العمر (دليل job 31 من التنانت الحي)

بيانات التنانت حسمت: job 31 كان **محاولة backfill حية شرعية** (cursor يتقدم إلى
6101، ‏175 جسمًا مستوردًا، ‏1844 مكتشفًا) تتجاوز 15 دقيقة بطبيعتها عند وتيرة
25 طلبًا/دقيقة — ومسند القِدم العمري كان «يستصلحها» في منتصفها برسالة كاذبة
«no progress > 15m» رغم التقدم الفعلي، فتدخل رقصة إيقاف/استئناف تطيل اللحاق
وتجعل رفض «already running» يبدو أبديًا أمام المشغّل. و`paused` **ليس** في مسند
الحجب أصلًا — `createJob` يستأنفه فورًا؛ لقطة «paused» كانت نافذة الإيقاف الزائف.

**القرار**: `sync_jobs.lease_at` (migration 013) يلمسه `checkpoint()` — الذي
يعمل أصلًا مرة كل ≤1ث في أي محاولة حية، بدمج اللمسة وقراءة حالة التحكم في
جولة واحدة (`UPDATE … RETURNING status`). مسندا الاستصلاح (`reconcileStale`
و`createJob`) يقيسان الآن **موت النبضة** (`COALESCE(lease_at, started_at,
created_at)`) لا عمر المحاولة: محاولة حية لساعة لا تُمسّ أبدًا؛ محاولة ميتة
تُستصلح كما قبل؛ والصفوف السابقة لـlease تتراجع إلى `started_at` بلا كسر.
حماية التزامن باقية حرفيًا (job حي يرفض تشغيلًا موازيًا — مُثبت). أثناء
backfill طويل يبقى الرفض صحيحًا ومؤقتًا بطبيعته: بعد اكتمال الـbackfill تصبح
الدورات قصيرة (ثوانٍ كل 120ث) وTest B يجد المسار حرًّا غالبًا.

## البريد المؤرشف: خط الأنابيب يبتلع أي مجلد مُدرَج ذاتيًا — والـprobe يحسم سلوك Zoho

متطلب المنتج: ابتلاع الأرشيف ذاتيًا بلا أي تدخل يدوي. **إثبات بالكود والاختبار**:
مجلد Archive مُدرَج في `/folders` يمرّ بنفس المسار الكامل ذاتيًا — اكتشاف،
upsert، ترقيم صفحات، **كشف الصفحة الأخيرة** (batch < PAGE_SIZE → backfill_done)،
مؤشر استئناف محفوظ (آمن عبر restart)، dedup بالبصمة v3، دوران بارد كل ≤15
دقيقة لا يُهجر أبدًا، وضبط وتيرة API. الاختبار
"archived mail in a listed folder is ingested autonomously" يثبت ذلك كاملًا
(نجح فور كتابته — أي أن فرضيات «تعيين مجلد غير مدعوم / نوع مستبعد / عيب ترقيم /
مؤشر بائد / فلتر مزامنة» ساقطة في كود Madar).

فإن غاب المؤرشف على التنانت الفعلي فالحسم عند حدود Zoho، وأداة
`scripts/archive-probe.js` القرائية تقرره بالدليل: جرد المجلدات كما يعيدها
Zoho حرفيًا (أسماء/أنواع/حقول)، ما ابتلعه Madar فعليًا لكل مجلد (عدّ + مؤشر)،
ومصفوفة مرشّحات archived-view مصنَّفة بنفس مصنِّف الإنتاج. ثلاثة أحكام ممكنة:
(أ) الأرشيف مجلد مُدرَج ⇒ مبتلَع أصلًا والفجوة توقيت دوران؛ (ب) خلف view
مخصص ⇒ الدليل جاهز لبناء تعيين virtual folder عليه؛ (ج) غير معروض في الـAPI
⇒ الرفض المصنَّف هو الإثبات، ويبقى تصدير eDiscovery مسار ذلك الركام.

## Virtual Archived Folder + انتظار التشخيص للـworker الحي

**دليل التنانت**: `messages/view?status=archived` يعيد 200 برسائل حقيقية ⇒
المؤرشف مدعوم API-يًا خلف view مخصص لا كمجلد مُدرَج. **القرار**: مجلد افتراضي
`zoho:archived` يظهر في `listFolders` ويمرّ **بنفس خط الأنابيب حرفيًا** (دوران
بارد، ترقيم، كشف الصفحة الأخيرة، مؤشر محفوظ، dedup بالبصمة v3 — فالرسالة
الموجودة أيضًا في مجلد Archive مُدرَج لا تتكرر أبدًا). جسد الرسالة ومرفقاتها
يُجلبان عبر مجلد الرسالة **الأصلي** (`sourceFolderId` من صف الـview). التفعيل
بالدليل: تينانت يرفض المعامل (4xx) تُسجَّل قدرته `unsupported:<classification>`
وتستمر الدورة — فشل المجلد الافتراضي لا يُفشل الصندوق أبدًا، والدورات التالية
تتخطاه بلا إعادة فحص. لا خطوة يدوية في أي مسار. مُثبت باختبار فاشل-أولًا
للتينانتين (المدعوم وغير المدعوم).

## المراجعة الهندسية الشاملة: آلة حالة واحدة بدل UPDATEs متناثرة

سؤال المالك: «ما البنية التي سمحت بهذه الفئة من العيوب أصلًا؟» الجواب:
انتقالات حالة الـjob كانت UPDATEs خام في سبعة مواضع، بلا خريطة شرعية، بلا
CAS، بلا سجل — فكانت كل مشكلة (زومبي الاكتمال، الالتباس paused/running،
إمكان الاستئناف المزدوج، إغلاق يقتل المحاولة، «لماذا هذا الـjob هكذا؟») عرَضًا
لهذا الغياب. **القرار المعماري**:

1. **كاتب واحد**: `transitionJob()` — خريطة انتقالات شرعية صريحة
   (queued→running/paused/cancelled؛ running→paused/completed/failed/cancelled؛
   paused→running/cancelled)، تنفيذ CAS
   (`WHERE status = ANY(expected) … RETURNING prev`)، وحدث في `job_events`
   (migration 014) بالفاعل والسبب. **سباق الاستئناف المزدوج صار مستحيلًا
   بنائيًا**: عمليتان تحملان نفس job المتوقف — واحدة فقط تفوز بـ
   paused→running والأخرى تُخبَر الحقيقة.
2. **كل حالة مفسَّرة**: `job_events` يجيب حرفيًا «لماذا يعمل/متوقف/تُخُطّي/
   استُرد/فشل/استؤنف» — يعرضه `job-inspect` (lifecycle) وسجل دورات الـworker
   يسجّل عند التخطي «busy» هوية الـjob الحاجب وعمر نبضته وهل هو صحي.
3. **ثوابت مفروضة في SQL**: النبضة `GREATEST(lease, now())` لا ترجع أبدًا؛
   المؤشر `advanceCursor` أحادي الاتجاه و`backfill_done` يثبت للأمام؛
   الاسترداد idempotent (تمريرة ثانية = لا شيء، بلا أحداث مكررة).
4. **إغلاق تعاوني حتمي**: SIGTERM يرفع علمًا؛ الـcheckpoint التالي (≤1ث)
   ينقل running→paused بسبب «graceful shutdown» والمؤشر محفوظ — إقلاعٌ تالٍ
   يستأنف من النقطة ذاتها. RESTART → AUTO RESUME → COMPLETED حتمية.
5. **استرداد إقلاع واعٍ بالـlease**: العملية الميتة تترك نبضة مجمّدة — كل
   running بنبضة أقدم من نافذة السماح (10ث) يُوقَف للاستئناف الفوري؛ محاولة
   بنبضة حية (CLI في حاوية أخرى نجت من إعادة تشغيل الخادم) لا تُمسّ.

مصفوفة اختبار كاملة تثبت السلاسل: السعيدة (queued→running→completed بأحداث
مسبَّبة)، الانهيار→الاسترداد→الاستئناف→الاكتمال، الإغلاق الرشيق→الاستئناف
التلقائي، سباق الاستئناف المزدوج (فائز واحد بالضبط)، idempotence الاسترداد،
رتابة المؤشر، واستحالة الانتقال غير الشرعي. 52/52.

   الآن: الطباعة للشاشة **أولًا** دائمًا، ثم محاولة الكتابة عبر سلسلة مسارات
   (`--out` ← `MADAR_DATA_DIR` ← `/var/lib/madar` القابل للكتابة في الحاوية ←
   `data/` للتشغيل المباشر) وفشل الكتابة تحذير لا انهيار.
2. **حوادث بلا أسماء**: ‏`status` كان يطبع عددًا فقط — التشخيص كان رهين ملف
   التقرير. الآن يطبع أنواع الحوادث وعدّها وآخر detail مباشرة، وحادثة التكرار
   تسمّي الصفوف الجانية (عنوان الصندوق، معرّف رسالة المزوّد، الـcanonicals،
   المجلدات — بلا مواضيع/أجساد).
3. **`--canary` بلا نص كان يعني بصمت «لا طُعم»** (فحص التوجيه يصير N/A دون
   تحذير) — الآن يولّد موضوعًا ويطبع بوضوح أن على المشغّل إرسال بريد حقيقي به.

ودرس منهجي وُثّق بشبكة انحدار: فرضيتي الأولى («المجلد الافتراضي يكرر occurrence
فيطلق تكرارًا زائفًا كل عيّنة») **نقضها الدليل** — القيد
`UNIQUE (mailbox_id, canonical_message_id)` يجعل نسخة المجلد الثاني مستحيلة
بنيويًا (والإدراج الثاني no-op مُقاس بـ`duplicate_prevented`). إذن تجميع الكاشف
الأعمى عن المجلد **صحيح ومقصود**: أي مجموعة >1 هي نفس رسالة المزوّد تحت
canonical-ين — انقسام بصمة، وهو فئة «التكرار» الحقيقية. اختباران جديدان:
اللا-تكرار البنيوي (إعادة استيعاب عبر مجلد ثانٍ = no-op)، والكاشف يرصد انقسامًا
مفتعلًا ويسمّي صفوفه — وإضافة folder_id للتجميع (إصلاحي الأول الخاطئ) تُفشل
الاختبار الثاني نصًا. ‏57/57. أنواع حوادث run 4 الحقيقية يكشفها `status` القادم.

## 1056 انقسام بصمة على المستأجر الحقيقي: حارس هوية المزوّد + المصالحة

أول `status` مُسمّى للحوادث كشف الحقيقة: ‏`duplicate_detected` في كل عيّنة،
‏`dupOcc: 1056` و`dupCanon: 0`، والعينات تسمّي الصفوف: نفس `provider_message_id`
في مجلدَي «Archived (Zoho)» والمجلد الحقيقي بـ**canonical-ين** (قديم 994/4514
مقابل جديد 66835+). أي أن المجلد الافتراضي Archived عند تفعيله أعاد استيعاب
رسائل مخزنة أصلًا كـcanonicals **جديدة**: عرض `status=archived` يعيد نفس
الرسالة بحقول منحرفة عن عرض المجلد (مرساة زمن البصمة على الأرجح — إحصاء
الانحراف في تقرير المصالحة يسمّي الحقل بدقة من بياناتك)، فتغيّر fp3 وانشقّ
canonical. هذا انتهاك حقيقي لشرط «لا canonicals مكررة» — والكاشف الأعمى عن
المجلد هو من أمسكه.

الإصلاح الجذري لا الترقيعي:

1. **حارس هوية المزوّد في `insertMessage`** (داخل المعاملة، قبل أي إنشاء):
   نفس الصندوق + نفس المزوّد + نفس `provider_message_id` = نفس الرسالة
   **مهما انحرفت البصمة بين العروض** — يُعاد استخدام الـcanonical القائم،
   والانحراف يُقاس (`provider_identity_reused` في fingerprint_metrics) لا
   يُبتلع. ‏Migration 016: فهرس `(mailbox_id, provider, provider_message_id)`
   (غير فريد — بيانات ما قبل المصالحة تحمل المجموعات المنشقة شرعًا).
2. **المصالحة** (`modules/mail/split-repair.js` + سكربت dry-run افتراضيًا):
   لكل مجموعة منشقة، يُحفظ canonical أقدم occurrence (تاريخ المنح والتدقيق
   والخيوط)، وقبل أي حذف يُنقذ ما يملكه المنشق حصريًا (مرفقات بمطابقة
   sha256+الاسم، وجسم مفقود)، ثم تُحذف occurrences المنشقة والـcanonical
   المنشق **فقط إن لم يعد يشير إليه شيء** (نسخ الأعضاء الموجهة تبقيه حيًّا —
   يُبلَّغ ولا يُمسّ). معاملة لكل مجموعة: idempotent وقابل للاستئناف.
3. **الاختبارات** (57/57): الحارس يمنع سكّ canonical ثانٍ لنفس رسالة المزوّد
   بزمن منحرف (فشل نصًا قبل الحارس — red موثّق)؛ الكاشف يظل يرصد الانقسامات
   القائمة (تُصنع بـSQL خام لأن المحرّك صار يرفض توليدها)؛ والمصالحة تُبقي
   occurrence واحدًا على الـcanonical الأقدم وتحذف اليتيم وتعيد صفرًا في
   التشغيل الثاني، وبعدها الكاشف يصمت.

## طبقة تكامل المحاسبة: واجهة آلة مستقرة فوق الصناديق المشتركة

المتطلب: الأنظمة المحاسبية تستهلك `finance@`/`billing@`/`tax@` عبر Madar
حصريًا — لا اتصال مباشر بـZoho. البناء (migration 017 + `integration.js` +
مسار `/api/integration/v1/*` قبل الجلسات):

- **مفاتيح آلة** بنطاق صناديق صريح لكل مفتاح: الإنشاء (أدمن، مدقَّق) هو منح
  الوصول الآلي — تناظرًا تامًا مع سياسة منح البشر. السرّ `mik_…` يظهر مرة
  واحدة ولا يُخزَّن (hash فقط + بادئة عرض)؛ الإبطال مدقَّق ويقتل المفتاح
  فورًا. خارج النطاق = 404 (anti-enumeration)، بلا مفتاح = 401.
- **معرّفات ثابتة**: mailbox id وoccurrence id هويات قاعدة لا يعاد
  استخدامها؛ canonicalId يمنع التكرار عبر الصناديق (وحارس هوية المزوّد يمنعه
  عند المنبع).
- **دلالة غير-المقروء**: مؤشر دائم **رتيب** (GREATEST) لكل (مفتاح، صندوق) —
  ‏GET messages بلا `after_id` يعيد ما بعد المؤشر، الإقرار بـPOST cursor،
  و`after_id=0` يعيد التاريخ كاملًا؛ فشل قبل الإقرار = إعادة نفس الرسائل
  (exactly-once لموضع المستهلك).
- **أمانة كاملة**: provider/rfc message id، المرسل والمستلمون (envelope لكل
  occurrence)، sentAt/receivedAt، المجلد، بيانات المرفقات وتنزيلها (النوع
  من فحص البايتات؛ المحجور 423).
- **قرار IMAP موثق** في docs/INTEGRATION-API.md: REST بمؤشر يغطي الاستهلاك
  المحاسبي بسطح أصغر؛ إن فُرض IMAP لاحقًا يُبنى كمحوّل فوق هذه الواجهة
  (المعرّفات الثابتة تسقط على UID مباشرة) لا كمسار بيانات ثانٍ.
- ‏TDD فوق HTTP الحقيقي (red مرصود قبل التنفيذ): الدورة كاملة — إنشاء مدقَّق،
  سرّ غير مخزَّن، نطاق، أمانة حقول، استنزاف غير-المقروء بعد الإقرار، رتابة
  المؤشر، منع التكرار على مستوى الواجهة، إبطال ⇒ 401. ‏58/58.

## المصالحة بشروط المالك: لا حذف نهائي — سجل دمج دائم + dry-run تنبّئي

قرار المالك: تنفيذ المصالحة يبدأ بـdry-run حصرًا، وبشروط ملزِمة أعيد بناء
الأداة عليها (اختبارات مشدَّدة أولًا — 59/59):

- **لا حذف نهائي**: كل صف يغادر الجداول الحية يُلتقط أولًا كـJSON كامل في
  `split_merge_log` (migration 018 — بلا FKs ليعيش بعد مصادره، لا يُشذَّب
  أبدًا): occurrence بكامل حقوله **بما فيها عضوية المجلد**، وcanonical
  بكامل حقوله. الاسترجاع ممكن دائمًا.
- **تدقيق**: صف `repair.split_merge` لكل تطبيق (أعداد المجموعات والصفوف
  والتعارضات)؛ التفصيل لكل مجموعة في سجل الدمج.
- **معاملة لكل مجموعة + idempotent + قابل للاستئناف**: إعادة التشغيل تجد 0
  مجموعات ولا تكرر صفوف السجل (مُثبت).
- **الأقدم هو المرجع**، والعلاقات تُنقل قبل أي إزاحة (مرفقات فريدة بمطابقة
  sha256+الاسم، جسم مفقود يُنسخ)، وcanonical المنشق المُشار إليه من صناديق
  أخرى (نسخ موجهة) **يبقى حيًّا** ويُدوَّن ذلك.
- **dry-run تنبّئي**: نفس استعلامات التحليل في الوضعين، فيجيب أسئلة المالك
  الأربعة قبل أي كتابة: عدد المجموعات، الـcanonicals المتأثرة، نص
  الاستراتيجية، وأصناف التعارضات (مشترَك عبر صناديق / مجموعات >2 /
  تصادمات مرفقات) + إحصاء انحراف الحقول (ومنه `canonical_hash_version`
  لحسم فرضية v2/v3 لجلسة التوثيق الموازية من البيانات نفسها).
- **ثابت الحالة النهائية** (مُثبت نصًا): provider + mailbox +
  provider_message_id ⇒ canonical واحد بالضبط، والحارس يبقيه.

## إطلاق الجامع: نداء عودة OAuth بلا جلسة + إعداد ثنائي الطور

عيب حقيقي كشفه تدفق «التفويض من ملف متصفح منفصل»: ‏`/oauth/callback` كان خلف
بوابة جلسة Madar — موافقة OAuth من ملف يحمل جلسة Zoho للجامع فقط كانت سترتد
401 ويفشل الربط. الإصلاح (TDD فوق HTTP حقيقي): النداء يُخدم قبل بوابة الجلسة؛
الحارس الفعلي يبقى state أحادي الاستخدام بهاش وTTL قصير أنشأه مشرف — بلا state
صالح الجواب 403 دائمًا (الاختبار يؤكد 403 لا 401 بلا أي كوكيز).

و`scripts/collector-setup.js` يضغط الإطلاق لخطوة بشرية واحدة:
- ‏`init`: يستنسخ بيانات الاعتماد **مشفرة داخل القاعدة** (لا فك، لا طباعة)
  إلى اتصال «Madar Capture» جديد، يسكّ state، ويطبع رابط تفويض واحدًا يُفتح
  في ملف الجامع ويوافَق عليه — هذه كل اليد البشرية. Idempotent.
- ‏`finish`: ينتظر تحول الاتصال connected، يشغّل الاكتشاف ويسجّل، يتحقق أن
  الجامع live-readable بمعرّف عامل، يفعّل Pilot+Sync، يدير أول دورة، ويطبع
  حكم الجاهزية مع تحذير صريح إن لم يكن العنوان في MADAR_COLLECTOR_ADDRESSES.
‏64/64.

## تصليب الجامع: دفتر أستاذ + منظّم مجلدات + إعادة محاولة + مراقبة

معمارية إنتاجية كاملة (docs/COLLECTOR-ARCHITECTURE.md — المخطط والعقود وخطتا

ورفضها يتدهور رشيقًا بقدرة مسجلة. المراقبة كاملة في live-sync status.

تكرار→سياسة الإعادة→حماية عدم التخفيض→العزل→العدادات).

## شجرة المجلدات مقدَّمًا + «المرايا»: عضوية الجامع في المجموعات بموافقة معزولة

بأمر المالك: (1) شجرة التنظيم كاملة تُنشأ في الجامع قبل وصول أول رسالة —
`ensureFolders` (أمر `collector-setup.js prepare-folders`): Failed/Unknown/Retry
+ ‏Processed-<localpart> لكل صندوق مشترك مسجّل. المنظّم لا ينشئ Retry أبدًا
(سطح إعادة يدوي لا هدف نقل) وينشئ Processed-* كسولًا — الآن الهيكل صريح.
قائمة المجلدات الحية تبذر الكاش أولًا: إعادة إنشاء اسم قائم 4xx على المستأجر
الحقيقي، وبدون البذر كانت إعادة تشغيل بريئة سنسجّل الكتابة unsupported زورًا.
(2) «المرايا» — `collector-mirror.js`: عنوان الجامع يصبح عضوًا في كل مجموعة
مشتركة فتصله نسخة معكوسة من بريدها. العقود: `plan` قراءة فقط وعضوية حيّة من
Zoho لا القوائم المخزّنة (درس فجوة ai@)؛ الكتابة عبر اتصال «Madar Groups
Admin» المخصص وحده بنطاق المجموعات فقط وبموافقة OAuth يعتمدها المالك بنفسه —
اتصال الإدارة لا يُرقّى أبدًا؛ إضافة فقط (لا حذف ولا تعديل لأحد)؛ idempotent؛
احتواء لكل مجموعة (رفض 4xx يُصنَّف ويُبلَّغ والبقية تمضي)؛ كل كتابة مدقَّقة في
audit_log؛ والتحقق إعادة قراءة حيّة لا الاكتفاء بـ200. الصدق المعماري:
العضوية شرط لازم لا كافٍ للتسليم — إعدادات المجموعة تقرر نسخ الأعضاء،
والحَكَم النهائي يبقى مسبار الالتقاط e2e لكل مجموعة. ‏66/66.

## صمّام أمان المرايا: قائمة سماح صريحة لا «كل الناقص»

بأمر المالك قبل أي تنفيذ إنتاجي: `apply` يرفض العمل بلا قائمة سماح صريحة
(`--include` أو `--file` بقائمة مراجَعة) — «كل المجموعات الناقصة» ليست موافقة
أبدًا. حلّ مجموعة الكتابة دالة نقية (`resolveWriteSet`) يستعملها العرض
والتنفيذ معًا فلا ينحرفان: المستبعَد سياسيًا (سبعة عناوين محددة بقرار المالك:
all@ بالنطاقين، ismail.yassin@، notifications@، system@،
officemailrestrictions@، access@) يُرفض حتى لو أُدرج صراحة ويُبلَّغ سببه —
رفعُه تغيير كود مراجَع لا راية CLI؛ الخطأ المطبعي يظهر unknown لا يُتجاهل؛
والمجموعة النهائية تُطبع بحرفها ويُشترط كتابة APPLY نصًا قبل أول كتابة.
غير المُدرج لا يُلمس إطلاقًا (مثبت اختبارًا على قوائم أعضاء المحاكي).
تبقى الضمانات السابقة: إضافة فقط، idempotent، تدقيق لكل كتابة، تحقق بإعادة
قراءة حيّة، واحتواء رفض المستأجر. ‏66/66.
