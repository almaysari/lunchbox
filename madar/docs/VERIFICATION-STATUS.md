## B. Locally infrastructure-verified — 25 اختبار PostgreSQL تكاملي ناجح (آخر دورة: 2026-07-17)

دورة التحقق المنفذة فعليًا: قاعدة فارغة → `npm run migrate` (طُبّق 001+002)
→ `migrate` ثانية (up to date) → `npm test` (25/25). تغطي إضافة إلى ما سبق:
سياسة platform_admin (إدارة بلا قراءة محتوى دون Grant)، سياسة 404 لمنع
التعداد، Canonicalization v2 واختبارات التصادم، خصوصية Envelope/BCC عبر
الصناديق، أمن FTS من الـOccurrences المصرّحة حصريًا، التزامن (بدءان
متزامنان = مهمة واحدة + Conflict)، Crash Recovery (running → paused)،
جاهزية Health بالحالتين، وCross-session CSRF. وتغطي: Schema، RBAC بجداول
حقيقية، القفل بعد محاولات فاشلة، تدوير الجلسات وإبطالها، CSRF، تشفير مصنّف
بنسخ مفاتيح + تدوير فعلي، oauth_states (تجزئة/انتهاء/استخدام واحد)،
Canonical/Occurrences (رسالة في صندوقين = canonical واحد بلا فقدان)،
مهام مزامنة (إيقاف مؤقت أثناء التشغيل، استئناف، إلغاء أثناء التشغيل)، حجر
المرفقات عند تعارض MIME المكتشف مع المعلن، فصل صلاحيتي العرض/التنزيل، رؤوس
أمان وRange، عقد التخزين كاملًا، أمن البحث داخل SQL، تعقيم التدقيق والأدلة،
وHealth. (السجل الأقدم أدناه من 2026-07-16 يبقى للتاريخ.)

### سجل 2026-07-16 (16 اختبارًا على النموذج السابق)

- كل الـMigrations من قاعدة فارغة + إعادة تشغيلها بلا أخطاء (checksum guard).
- إنشاء المستخدمين والأدوار وتسجيل الدخول (scrypt N=2^15، رفض كلمات قصيرة).
- توقيع كوكيز الجلسات HMAC ورفض المُعدّل منها.
- تشفير أسرار الاتصالات AES-256-GCM at-rest وفك صحيح، وعدم تسريبها من الـAPI.
- إنشاء 20 Shared Mailboxes من الـFixture دون تكرار عند إعادة الاكتشاف.
- Alias uniqueness (alias لا يصبح صندوقًا ثانيًا أبدًا).
- تعقيم أدلة الكشف وسجل التدقيق (لا توكنات مخزنة).
- Mailbox grants ومنع الوصول بين المستخدمين (403 فعلي).
- بوابة المزامنة المزدوجة (pilot + explicit start)، تشغيل جزئي، Resume من
  المؤشر المحفوظ، صفر تكرار (250 رسالة عبر تشغيلين).
- بقاء sync_state بعد إسقاط الـPool (محاكاة Restart).
- Cancellation مع حالة قابلة للاستئناف.
- تخزين المرفقات: مفاتيح غير قابلة للتخمين، منع Traversal، حد حجم، SHA-256،
  خارج public، وتنزيل مقيد بالصلاحية.
- بحث FTS (tsvector/GIN) مقيد بصلاحيات المستخدم.
- healthz يعكس توفر القاعدة.

## A. Mock-verified (Mock + Fixtures — ليس إثباتًا عن حساب Zoho الحقيقي)

- Mock Discovery: اكتشاف مؤسسي كامل ضد محاكي Zoho محلي.
- Fixture Validation: مطابقة 20/20 مع القائمة المرجعية **ضد الـMock فقط**.
- تصنيف الأنواع (shared_mailbox / user / distribution_list / stream_group).
- التقاط الـAliases وتخزينها ومنع تسجيل alias كصندوق مكرر.
- استخراج مستويات الوصول الثلاثة والأعضاء والمشرفين وعدادات الـModeration.
- الفصل بين طابور المراجعة والأرشيف (moderation ≠ archive).
- منع التكرار على مستوى المنصة (معرّف المزوّد + بصمة Message-ID).
- محلل eDiscovery (ZIP/EML/MIME) واستيراد الأرشيف بالمجلدات والمرفقات.
- مزامنة Pilot قراءة-فقط ببوابة صريحة **باستخدام بيانات Mock**.
- تدفق OAuth كود-إلى-توكن **ضد الـMock** (وليس ضد خوادم Zoho).
- 13 اختبارًا آليًا تغطي ما سبق.

## C. Live Zoho-verified — ✅ الاكتشاف مثبت (2026-07-17)، والمزامنة لم تبدأ

كل بند أدناه مدعوم بدليل معقّم في `detection_reports` (mailbox_id=0 للتقرير
المؤسسي + تقرير لكل صندوق) وبالأدلة التي راجعها الأدمن من اللوحة:

- **OAuth الحقيقي** ✅ — التصريح بحساب `super_admin` (بريده الأساسي
  `m.almaysari@exoticcolors.me`)؛ `/api/accounts` أعاد 200.
- **الـOrganization ID الحقيقي** ✅ — `zoid=769245245` مستخرج من
  `accounts.policyId.zoid` (مسار بديل مُوثّق في الدليل بحقل `zoidSource`).
  ملاحظة مثبتة: `GET /api/organization` نفسه يرفض بـ401 INVALID_OAUTHSCOPE
  حتى لحساب super_admin — غير معطِّل بعد المسار البديل.
- **استجابة Groups API الفعلية** ✅ — الشكل الحقيقي `data:{count,groups,domains}`
  (وليس مصفوفة)، الحقول الفعلية `mbtype:"2"`/`mailboxId`/`accessType`
  (Public/Moderated/Organization)/`mailModerationcount`/`mailGroupMemberList`؛
  الصفحة الأولى ناقصة والاكتمال تحقق باتحاد عضويات `groupList` من
  `organization/{zoid}/accounts` ثم `groups/{zgid}` لكل مجموعة مستعادة.
- **اكتشاف الصناديق العشرين** ✅ — Expected 20 / Matched 20 / Missing 0،
  مع 13 مجموعة بريدية إضافية خارج المرجع و7 مجموعات IAM بلا بريد (أقسام)
  استُبعدت من السجل تصنيفًا (`org_group`). فحوص التكامل صفرية (لا تصادم
  aliases، لا معرفات مكررة، لا عناوين مزدوجة المصدر).
- **قائمة حسابات المؤسسة** ✅ — `organization/{zoid}/accounts` أعادت 89 حسابًا.
- **القراءة الحية لرسائل الـShared Mailbox** — حُسم السؤال المفتوح **سلبًا
  بالدليل**: لا يوجد endpoint رسمي مختبَر يعيد رسائل الصناديق المشتركة
  (السجل يظهر `no_live_api` لكل صندوق مجموعة، والاستراتيجية المقترحة
  استيراد أرشيف eDiscovery + طابور الـModeration للمحتجز فقط).

غير مثبت بعد (لا يُغلق قبل اختباره فعليًا):

- Pilot Sync قراءة-فقط على صندوق حقيقي (بانتظار موافقة صريحة).
- استيراد أرشيف eDiscovery حقيقي (ZIP من Zoho) واكتمال تاريخي.
- تنزيل مرفقات حقيقية (محظور في مرحلة الاكتشاف بالسياسة).
- حدود معدل Zoho الفعلية تحت حمل مزامنة كاملة.
- Resume/Recovery ضد انقطاعات Zoho الحقيقية.

## كيف يُقفل ما تبقى

البنود «غير المثبتة بعد» في القسم C تُغلق حصريًا بتشغيل حقيقي ناجح لكلٍّ
منها (Pilot Sync معتمَد، استيراد أرشيف فعلي، …) مع دليله المعقّم في
`detection_reports`/`sync_jobs`. لا يُعتبر أي بند مثبتًا قبل ذلك.

## ضمانات الفصل بين الوضعين (مطبقة في الكود)

- الوضع التجريبي يستخدم قاعدة PostgreSQL منفصلة كليًا (مثل `madar_demo`
  عبر `DATABASE_URL`) — بيانات الـMock لا يمكن أن تتسرب إلى قاعدة Live.
- القائمة المرجعية (`test/fixtures/expected-mailboxes.json`) تُقرأ فقط في
  خطوة المقارنة بعد الاكتشاف؛ لا يوجد أي مسار كود ينشئ صناديق منها.
- الواجهة تعنون النتائج صراحةً: «Mock Discovery — ليست Zoho الحقيقية» في
  demo، و«Live Zoho API Discovery» في live.
- الجدولة التلقائية لا تلمس أي صندوق لم يبدأ الأدمن مزامنته يدويًا
  (`sync_enabled` لا يُرفع إلا بزر البدء الصريح).
